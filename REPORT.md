## 2. Назначение проекта

Cloud Team Project — учебное веб-приложение на Python (Flask), которое по HTTP отдаёт каталог облачных сервисов с моделями IaaS, PaaS и SaaS. Приложение упаковано в Docker-контейнер и может быть запущено на любой машине с Docker: локально, на виртуальной машине или в облаке.

```
### Вариант 2. Локальный запуск без Docker

```

## 4. Использованные элементы Markdown

| Элемент | Где применён |
|---------|--------------|
| Заголовки `#`, `##`, `###` | Иерархия разделов документа |
| Выделение `**текст**` | Название проекта, модели IaaS/PaaS/SaaS, предупреждение |
| Маркированный список `-` | Цели проекта, технологии, требования |
| Нумерованный список `1.` | Пошаговая инструкция запуска в Docker |
| Таблицы | Архитектура, эндпоинты, конфигурация, автор |
| Ссылки `[текст](url)` | Технологии, документация GitHub, файл архитектуры |
| Встроенный код `` `...` `` | Имена файлов, переменные, пути |
| Блоки кода ```` ``` ```` | Команды запуска, структура репозитория |
| Цитата `>` | Предупреждение о секретных данных |

Всего использовано 9 элементов разметки (требуется не менее 4).

## 5. Архитектурные компоненты

1. **Пользователь** — отправляет HTTP-запросы через браузер или `curl`.
2. **Веб-приложение (Flask)** — обрабатывает запросы на эндпоинтах `/`, `/health`, `/services` и формирует JSON-ответ.
3. **Хранилище данных** — файл `app/data/services.json` с каталогом облачных сервисов.
4. **Конфигурация** — параметры запуска (`APP_PORT`, `DATA_FILE`) из переменных окружения; пример лежит в `config/.env.example`.
5. **Docker-контейнер** — изолированная среда, в которой находятся Python, зависимости и код приложения. Образ собирается по `Dockerfile`.

## 7. Вывод

В ходе работы был подготовлен README.md для учебного облачного проекта с помощью языка разметки Markdown. Документ описывает назначение проекта, его архитектуру, структуру репозитория, используемые технологии и пошаговую инструкцию запуска как в Docker-контейнере, так и локально.

Документация играет ключевую роль в сопровождении облачного проекта: новый участник команды может разобраться в системе и запустить её без изучения всего исходного кода. Пошаговая инструкция делает развёртывание воспроизводимым, а описание конфигурации и отказ от хранения секретов в репозитории повышают безопасность проекта.

## 8. Ответы на контрольные вопросы

**1. Для чего используется README.md?**
Это главный файл описания проекта: GitHub автоматически показывает его на странице репозитория. Из него посетитель узнаёт, что это за проект, зачем он нужен, как его запустить и использовать.

**2. Какие элементы Markdown структурируют документацию?**
Заголовки разных уровней, маркированные и нумерованные списки, таблицы, блоки кода, ссылки, выделение текста и цитаты.

**3. Что включить в инструкцию по запуску?**
Предварительные требования (ПО и версии), команды клонирования, установки зависимостей, сборки и запуска в правильном порядке, параметры конфигурации, способ проверки работы и порядок остановки.

**4. Почему нельзя размещать пароли, токены и ключи в репозитории?**
Репозиторий может быть публичным или стать доступным посторонним, а история Git сохраняет файлы даже после удаления. Утёкшие ключи позволяют злоумышленнику получить доступ к облачным ресурсам, данным и счёту. Секреты хранят в переменных окружения, файлах `.env` (внесённых в `.gitignore`) или менеджерах секретов.

**5. Как документация упрощает командную разработку?**
Все участники одинаково понимают архитектуру и правила работы, новые разработчики быстрее включаются в проект, снижается число вопросов и ошибок при развёртывании, а знания о системе не теряются при смене команды.
